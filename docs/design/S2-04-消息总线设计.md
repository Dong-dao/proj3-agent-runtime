## 1. 题面痛点与 OS 出处

**痛点**：Agent 间通信若每条消息都深拷贝上下文，通信成本随消息量线性放大；且消息无 ID 无法追踪，容易丢、重。

**OS 出处**：共享内存 + 消息队列（System V / POSIX IPC）——发送方把数据放进共享区，接收方按引用读取，避免内核态与用户态之间的重复拷贝。我们迁移「共享区 + 引用传递、不做序列化拷贝」这条思想。

## 2. 机制定义

- **消息结构**：每条消息带 `msgid / sender / receiver / ts / payload_ref`，`payload_ref` 指向共享上下文区的 `ctx_id`，不是数据副本。
- **共享上下文区**：复用 `ContextStore` 的不可变前缀对象；消息传引用，接收方 `acquire` 后读取，用完 `release`。
- **不丢不重**：`msgid` 全局递增唯一；投递记录 `delivered` 集合，重复投递被拒；队列非空时每次 `recv` 取队首并标记已投递。

## 3. 为什么不做序列化拷贝（必答项）

| 方案 | 后果 |
|---|---|
| 每条消息 pickle/JSON 序列化整份上下文 | 通信字节数线性放大、拷贝次数与消息数正相关，COW 省下的拷贝全部吐回去 |
| 共享区 + 引用传递（本方案） | 消息只带 `ctx_id`；多个接收方共享同一对象，靠 `refs` 管理生命周期，拷贝只在写入时发生 |

结论：**消息总线与 COW 上下文是同一条优化链**——总线负责传引用，COW 负责在写入时才复制，二者合起来才省得掉拷贝。

## 4. 状态不变量

| 编号 | 不变量 | 由哪段代码保证 | 怎么测 |
|---|---|---|---|
| M1 | 消息 ID 唯一 | 全局递增序号 | 发 N 条，断言 msgid 集合大小 = N |
| M2 | 消息不丢 | 队列 + 投递记录 | 发 N 收 N，断言全部收到 |
| M3 | 消息不重 | `delivered` 集合去重 | 重复 recv 同一 msgid，断言被拒 |
| M4 | 不做序列化拷贝 | payload 只存 ctx_id 引用 | 断言消息体无字节副本、`copy_count` 不因发消息增加 |
| M5 | 引用生命周期完整 | 接收方 acquire/release 成对 | 投递后断言 `refs` 正确增减 |

## 5. 可数证据

| 证据 | 采集位置 | S2 验收期望 |
|---|---|---|
| 消息条数 `message_count` | `MessageBus.stats()` | 发 N 条 = N |
| 通信字节数 `comm_bytes` | `MessageBus.stats()` | 引用传递下远小于序列化方案 |

## 6. 与 T2 实现的对接点

T2 已落地 `runtime/bus.py`：`MessageBus` 类、`stats()` 返回 `message_count / comm_bytes`（S1 骨架，`_sent` 计数）。S2 实现：①补 `send/recv` 与队列、`msgid` 序号、`delivered` 集合；②payload 存 `ctx_id` 引用并接 `ContextStore`。**不改 `stats()` 字段与契约①签名**。

## 7. 用户态边界声明

| 作品里的机制 | OS 原型 | 必须如实声明的边界 |
|---|---|---|
| 消息总线 | 共享内存、消息队列 | 进程内逻辑总线，不是内核 IPC；不做跨机通信、不做序列化 |
