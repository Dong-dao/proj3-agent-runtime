## 1. 题面痛点与 OS 出处

**痛点**：多 Agent 系统是黑盒——看不到任务图、状态、资源占用，出了问题无法干预。

**OS 出处**：`/proc` 与 cgroup 统计接口——内核把运行状态暴露为只读文件视图，工具可读可查；同时提供控制信号（kill/stop/cont）做受控干预。我们迁移「只读快照 + 受控指令」这条设计，不挂真实 procfs。

## 2. 机制定义

- **只读快照 `snapshot()`**：导出任务图（DAG 结构）、各 Agent 状态与配额、句柄表、上下文引用、七项指标当前值。快照是某一时刻的一致视图，**导出动作本身不改变调度状态**。
- **控制指令**：`pause / resume / kill` 三个指令走统一入口，只作用于目标 Agent，记录指令日志与生效延迟。
  - `pause`：目标 Agent 暂停被派发；
  - `resume`：恢复派发；
  - `kill`：目标 Agent 走 `transition → FAILED`，触发句柄回收（与故障域熔断同一回收路径）。

## 3. 快照字段结构（对接 T2 已落地实现）

T2 `runtime/observer.py` 的 `snapshot()` S1 已返回：
```
agents: { agent_id: {state, quota, handles, ctx_refs} }
agent_counters:    AgentTable.stats()
resource_counters: ResourceManager.stats()
context_stats:     ContextStore.stats()
scheduler_stats:   Scheduler.stats()
```
S2 在此基础上补：任务图 DAG 快照、七项指标当前值、故障域状态。字段名沿用现有 `stats()`，不新增顶层字段以外的破坏性改动。

## 4. 状态不变量

| 编号 | 不变量 | 由哪段代码保证 | 怎么测 |
|---|---|---|---|
| O1 | 导出只读不改状态 | `snapshot()` 内无状态写入 | 连续两次 snapshot，断言调度状态与计数未变 |
| O2 | 快照一致 | 一次调用内取同一时刻各模块 stats | 断言快照内 agent 数与 table 一致 |
| O3 | 指令只作用目标 | 三个指令都带 agent_id 并校验 | pause A，断言 B 状态不变 |
| O4 | 指令留痕 | 每次指令记日志与时间戳 | 断言有指令日志、可算生效延迟 |
| O5 | kill 触发回收 | kill 走 FAILED 单一入口 | kill 后断言句柄归零 |

## 5. 可数证据

| 证据 | 采集位置 | S2 验收期望 |
|---|---|---|
| 快照 JSON | `Observer.snapshot()` | 含任务图/状态/资源/命中率四项 |
| 控制指令日志 | Observer 指令入口 | pause/resume/kill 各留一条带时间戳日志 |
| 生效延迟 | 指令时刻到状态变更时刻 | 非 null、合理正数 |

## 6. 与 T2 实现的对接点

T2 `runtime/observer.py`：`Observer(table, resources, context_store, scheduler)` 与 `snapshot()` S1 已实现；`pause/resume/kill` 三个方法 S1 抛 `NotImplementedError`，注释写明「S2 交付」。S2 实现这三个方法并补 DAG/指标字段，**不改构造签名与 `snapshot()` 已有字段**。

## 7. 用户态边界声明

| 作品里的机制 | OS 原型 | 必须如实声明的边界 |
|---|---|---|
| /proc 式导出 | procfs、cgroup 统计 | 不是真挂 procfs，是同构只读 JSON 视图 |
| 控制指令 | kill/stop/cont 信号 | 用户态逻辑控制，不产生真实信号与内核态切换 |
