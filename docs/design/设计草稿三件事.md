## 第一件：状态不变量

**总纲**：状态机是本作品的地基，四条不变量每一条都要能回答「由哪段代码保证、怎么测」两问。

| 编号 | 不变量 | 由哪段代码保证 | 怎么测 |
| --- | --- | --- | --- |
| I1 | 任一时刻状态唯一 | `agent.py` 中 Agent 只有一个 `state` 字段，且所有写入必经全局 `transition()`；模块内禁止直接赋值 | 并发发起两次转换，断言最终只有一个值生效、日志只有一条成功迁移 |
| I2 | 阻塞只能回到就绪 | `transition()` 查转换矩阵，BLOCKED 出边只开放 READY 与 FAILED | 对 BLOCKED 发起 → RUNNING，断言抛 `E_ILLEGAL_TRANSITION` 且有一条拒绝日志 |
| I3 | 失败为终态、不可回退 | 矩阵中 TERMINATED / FAILED 行全部为 ✗，`transition()` 对终态直接拒绝 | 对两个终态各发 6 种转换尝试，断言全部被拒 |
| I4 | 终止后句柄全部回收 | `transition()` 进入终态分支强制调用 `handle.release_all(agent_id)` 并记回收数 | 终态后断言该 owner 句柄表记录为 0、回收计数 = 持有数 |

**补充不变量（跨模块）**：
- 依赖未满足的任务不入就绪队列：由 `scheduler.next()` 只对 `ready_set()` 返回的任务派发保证。
- 同一任务不重复派发：由派发时立即 `READY → RUNNING` 保证，第二次 `next()` 不会再看非 READY 任务。

## 第二件：调度依据（11/21 先从这里交排序键说明）

### 2.1 为什么不用 FIFO

FIFO 按到达顺序派发，有三个硬伤：
1. **依赖盲**：队首任务依赖未满足时，FIFO 要么空转、要么违规派发；依赖图要求的是「就绪集合内选择」，不是「全局队列顺序」。
2. **时延无差别**：一个长任务（slice 大）排在前面会把后面的短任务堵死，短任务的等待时间不可控，deadline 违约数高。
3. **无公平账本**：无法表达「长任务一直让路会饿死」这件事，也没有配额概念。

### 2.2 EEVDF 思想怎么迁到依赖图

题面点名 CFS，但目标平台 openEuler 24.03 LTS SP3 是 Linux 6.6 内核，**6.6 起调度器已换成 EEVDF**。我们迁移的是它的两个核心概念：

- **eligible（应得份额未透支）**：EEVDF 用 `lag = 应得 - 已用` 判断一个任务是否「有资格」被选中。我们把它变成用户态配额账本 `lag(t) = quota_earned(t) - quota_used(t)`，并要求 `lag >= 0` 才算 eligible。这是思想迁移，不是移植内核实现，`lag` 与 `slice` 都是我们自己定义的逻辑量。
- **virtual deadline 最早优先**：EEVDF 在每个任务的「应得时间点」附近开一个虚拟 deadline，选最早者。我们把它迁进依赖图，让「就绪 + 关键路径长」的任务 deadline 更近、优先被选中，缩短总完成时间。

排序键定义（S1 冻结 v1）：

```text
lag(t)      = quota_earned(t) - quota_used(t)        用户态逻辑账本
eligible(t) = deps_ready(t) and lag(t) >= 0          依赖满足且未透支
slice(t)    = 任务声明的时间片预算（stub 下固定）
weight(t)   = f(配额, 关键路径剩余长度)              关键路径越长权重越高
vd(t)       = eligible_time(t) + slice(t) / weight(t)
排序键      = (eligible, vd, seq)                     seq 递增提交序号，决定论兜底
```

每轮从 eligible 集合取 `vd` 最小者派发。相比 FIFO：短任务 `slice` 小、`vd` 近，不会被长任务堵死；`lag` 账本保证长任务不会一直饿死；`weight` 让关键路径长的任务提前。

### 2.3 手算对拍示例（本人手算留档，供答辩与自证）

设某轮有 3 个任务已就绪（deps 均满足），参数如下，`eligible_time` 均取 0（同一轮进入）：

| 任务 | slice(ms) | weight | quota_earned | quota_used | lag | eligible |
| --- | --- | --- | --- | --- | --- | --- |
| A | 30 | 2 | 10 | 4 | 6 ≥ 0 | 是 |
| B | 10 | 1 | 10 | 12 | −2 < 0 | **否（透支）** |
| C | 20 | 2 | 10 | 10 | 0 ≥ 0 | 是 |

逐步计算 `vd = eligible_time + slice / weight`：
- A：`0 + 30 / 2 = 15`
- B：`eligible = 否`，不参与本轮排序（不计算 vd）
- C：`0 + 20 / 2 = 10`

排序键 `(eligible, vd, seq)`，B 不 eligible 直接排除，A 与 C 比较 vd：C(10) < A(15)。

**派发顺序：C → A**，B 留在队列等 `lag` 回正（下一个配额周期）再 eligible。

**FIFO 对照**：若按提交序 A、B、C，则先派 A(30ms)，再轮到 B——但 B 已透支且可能依赖未满足，会空转或违规；C 排第三，总等待 = A 的 30ms + B 的阻塞。依赖调度版本先派 C、A，短任务不被长任务堵死，且不派透支任务。这就是「为什么不用 FIFO」的可数例子。

> 手算结论：本轮 vd 值 A=15、C=10；eligible 集合 = {A, C}；派发序 C→A；B 因 lag=−2 被排除。实现出来的 `scheduler.next()` 在同样输入下必须给出同样结果，否则单测不通过。

### 2.4 换一种排序键会怎样（答辩追问必备）

| 换成 | 后果 |
| --- | --- |
| 纯优先级队列（weight 最高优先） | 简单，但低权重长任务持续饿死；没有 lag 账本，不公平；无法表达时延约束 |
| 仅 EDF（最早 deadline，不含 lag） | 透支任务仍可能被选中，配额失控；缺少公平维度 |
| FIFO | 见 2.1：依赖盲、短任务被堵、无公平账本 |
| 我们的 (eligible, vd, seq) | 依赖满足 + 未透支 + 时延感知三者兼顾；seq 保证决定论 |

### 2.5 三句话底线

1. 这是**思想迁移，不是移植内核 EEVDF**。
2. `lag` 与 `slice` 是用户态逻辑量，单位由我们自己定义。
3. `seq` 是决定论兜底，同键按提交序，不用随机数。

## 第三件：资源抽象边界

### 3.1 四类资源统一到 Resource Handle

模型调用（LLM）、工具调用（TOOL）、文件（FILE）、内存配额（MEMORY）长得不一样，但申请方式完全一样：都经 `acquire(agent_id, kind, perms, quota)` 拿到 `ResourceHandle`。这就是「一切皆句柄」从 OS 文件描述符表迁移过来的抽象。字段与签名见契约①第三节。

| 资源 | kind | perms 典型值 | 配额含义 |
| --- | --- | --- | --- |
| 模型调用 | LLM | EXEC | 允许调用的 token / 次数预算 |
| 工具调用 | TOOL | EXEC | 工具调用次数 |
| 文件 | FILE | READ / WRITE | 读写字节数或句柄数 |
| 内存配额 | MEMORY | READ / WRITE | 逻辑账本额度（非真实内存限制） |

### 3.2 越权与异常返回什么错误码

错误码集合固定，语义不可改（契约①第三节）：

| 场景 | 错误码 | 处理 |
| --- | --- | --- |
| 越权（perms 不含所请求权限） | `E_PERM` | 拒绝并记日志 |
| 超额（used + amount > quota） | `E_QUOTA` | 拒绝并记日志 |
| 伪造 / 过期 / 非 owner 句柄 | `E_BAD_HANDLE` | 拒绝并记日志 |
| 已 CLOSED 句柄 | `E_CLOSED` | 拒绝并记日志 |

### 3.3 句柄何时回收

1. **显式释放**：`release(handle_id, agent_id)` 把 `refs` 减 1，归零置 CLOSED。
2. **终态回收**：Agent 进入 TERMINATED / FAILED 时，`transition()` 强制调 `release_all(agent_id)`，回收该 owner 全部句柄并记回收数（对应不变量 I4）。
3. **边界声明**：这是用户态句柄对象，**不是内核 fd、不跨进程传递**；配额是逻辑账本，不是真实内存限制。这一条要原样写进设计文档边界声明节。
