# 调度排序依据（S1 v1→v2，T2 陈苗苗）

> 对应本周规划 11/20-11/21 交付项：「scheduler.py v1：依赖未满足不入队、同一任务不重复派发」「调度器 v2：关键路径长的任务优先，写出排序依据」。验收：排序键有文字依据。
> 排序键本身冻结在契约① 第 5 节，本文是对「为什么这样排」的文字依据，G1 互讲备用。

## 一、v1（11/20）：先把不变量做对

v1 只保证两条调度不变量，排序退化为提交序（FIFO）：

1. **依赖未满足不入队**：`_refresh_ready()` 只把 deps 全部进入 done 集合的任务从 CREATED 转 READY。图侧依据是 `graph.ready_set(done)`；调度侧依据是 `_pending` 集合只在依赖满足时摘出。
2. **同一任务不重复派发**：`next()` 选中即摘出就绪队列 + `_dispatched` 集合双保险；`on_complete()` 只处理在 `_dispatched` 中的任务。

这两条是 11/20 验收「3 Agent 有依赖有并行、状态迁移日志完整」的成立前提：没有它们，依赖图会被乱序击穿、日志里会出现同一 Agent 的二重状态。

## 二、v2（11/21）：排序键 (eligible, vd, seq) 的文字依据

**迁移的是思想，不是内核代码。** 题面参考资料点名 Linux CFS，但目标平台 openEuler 24.03 LTS SP3 基于 Linux 6.6 内核——6.6 起主线上已换 EEVDF 调度器。我们从 EEVDF 迁移两个核心概念：

- **lag（应得份额账本）**：`lag(t) = quota - used_slice(t)`。`eligible = deps_ready and lag >= 0`：依赖满足且未透支配额的任务才可派发。对应 EEVDF 用 lag 判断「应得份额是否被透支」；我们的 lag 是用户态逻辑账本，不是内核 vruntime。
- **virtual deadline（虚拟截止期）**：`vd(t) = ready_time + slice_ms / weight(t)`。每轮从 eligible 集合取 vd 最小者派发。对应 EEVDF「最早虚拟 deadline 优先」，兼顾公平与时延。
- **seq（提交序号）**：同键按提交序，不用随机数、不用系统时间。这是决定论兜底，保证同一负载重复运行结果一致（契约② 的可复现性质）。

**为什么关键路径长的任务优先**：weight 由应用声明，bench 按 `graph.critical_path_remaining()` 声明 weight（P1 策略上浮——Runtime 只提供机制，应用声明策略）。关键路径长者 weight 大、`slice/weight` 小、vd 近，于是先被派发，总完成时间缩短；同时 slice 小的时延敏感任务 vd 也近，不会被长任务堵死。相比纯 FIFO：短任务不再排队等长任务；相比简单优先级队列：lag 账本保证长任务不会因一直让路而饿死。

**换一种排序键会怎样**（互讲预答）：
- 换成 FIFO（v1 基线）：短任务可能堵在长任务后面，makespan 变差；本仓库 bench 首轮数据里 serial=60ms、fifo=50ms，本负载规模下 vd 与 fifo 打平（50ms），差距要在 S3 更深负载上拉开——这是如实记录，不为数据好看造差异。
- 换成纯最早 slice 优先（SJF）：需要预知 slice 且长任务会饿死，lag 条款恰好防饿死。
- 换成 LPT（最长优先）：总完成时间接近，但时延敏感任务等待时间无界，deadline_miss 上升。

## 三、S1 已知口径占位（S2 契约② 冻结时统一）

- `deadline_miss`：S1 用「完成时刻 > ready_time + slice × 10」占位，系数待契约②冻结。
- `sched_overhead_pct`：调度器真实 CPU 耗时 / 真实墙钟；makespan 用模拟时钟。两个时间基不一致，S2 统一。
- `peak_rss_mb`：Windows 上无 `resource.getrusage`，用 tracemalloc 峰值代替，S2 在 openEuler 上跑数时切回 getrusage 并记录两口径。
